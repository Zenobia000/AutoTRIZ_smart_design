# 🔍 問題拆解工作坊：RD 通用需求結構化思考

## 🎯 為什麼要拆解 RD 的需求？
想像 RD 在設計產品時，如果只想著「我要改進設計」，卻沒有具體的方向或步驟，可能會浪費時間在試錯上。將需求拆解成明確的問題和任務後，就能有系統地解決問題，縮短設計迭代週期，提高效率。

## 🏗️ 拆解的三個層次

### 第一層：問「為什麼」(Why)
**目的**：確認 RD 真正要解決的問題

**範例**：
- 原始需求：「我要改進一體機設計」
- 問為什麼：「為什麼需要改進設計？」
- 真正問題：「因為現有設計成本過高、重量太重、軸向太長，無法量產」

**練習**：
```
我的需求是：改進產品設計
我為什麼需要這個：因為現有設計無法滿足量產需求（成本、重量、尺寸問題）
真正的問題是：如何在設計初期就找到降成本、減重、縮短軸向的可行方向
```

### 第二層：問「什麼」(What)
**目的**：定義 RD 具體要做什麼

**思考框架**：
1. **輸入**：RD 能提供什麼資料？
2. **處理**：系統或工具需要做什麼？
3. **輸出**：RD 希望得到什麼結果？

**範例**：
- 輸入：現有設計的 STEP 檔案、BOM 表、設計約束（扭矩、空間、成本上限）、專案對照表、專利搜尋結果
- 處理：分析設計特徵、比對過往案例與專利、進行多目標權衡（成本 vs 重量 vs NVH）、生成設變建議
- 輸出：多維度比較報告、設計審查清單、最小打樣建議、可追溯的證據鏈

### 第三層：問「怎麼做」(How)
**目的**：確定實現的方法

**拆解原則**：
- **由大到小**：大目標 → 子任務 → 具體行動
- **由外到內**：RD 使用體驗 → 系統功能 → 技術細節
- **按時間順序**：第一步 → 第二步 → 第三步

## 🛠️ 實戰演練：RD 設計改進需求拆解

### Step 1: RD 使用者旅程拆解
```
1. RD 上傳現有設計檔案（STEP、BOM）
2. RD 輸入設計約束（扭矩、空間、成本上限）
3. RD 提供專案對照表與專利搜尋結果作為參考
4. 系統分析設計特徵並生成設變建議
5. RD 收到多維度比較報告與設計審查清單
6. RD 根據報告選擇設變方向並規劃最小打樣實驗
7. RD 回饋結果，系統更新對照表形成閉環學習
```

### Step 2: 系統功能拆解
```
前端部分：
├── 使用者介面（檔案上傳、約束輸入）
├── 結果展示（比較報告、審查清單）
└── 回饋機制（意見輸入、對照表更新）

後端部分：
├── CAD 檔案解析（STEP 結構特徵提取）
├── 多目標權衡分析（成本、重量、NVH 等）
├── 知識檢索（專案對照表、專利數據庫）
├── 建議生成（設變方向、打樣建議）
└── 證據鏈記錄（建議與數據來源關聯）
```

### Step 3: 開發任務拆解
```
第一階段（基礎功能）：
├── 建立檔案上傳與解析框架
├── 設計基本使用者介面
└── 實現初步設計特徵提取

第二階段（核心功能）：
├── 整合多目標權衡算法
├── 實現知識檢索與建議生成
└── 完成比較報告與審查清單模板

第三階段（進階功能）：
├── 新增回饋閉環與對照表更新機制
├── 優化使用者體驗與報告視覺化
└── 擴展專利數據庫與外部知識整合
```

## 🎯 拆解檢查清單
完成拆解後，檢查是否滿足：
- [ ] **具體可行**：每個任務都知道怎麼做
- [ ] **時間合理**：每個任務不超過一天工作量
- [ ] **相互獨立**：任務之間依賴關係清楚
- [ ] **可以測試**：每個功能都能驗證是否完成
- [ ] **優先順序**：知道哪些重要，哪些可以延後

## 💡 拆解技巧

### 1. 5W1H 法
- Who（誰）：機構 RD、系統 RD、製造工程、PM、採購等
- What（什麼）：改進產品設計，生成設變建議與比較報告
- When（何時）：設計初期（Day 1），避免事後試錯
- Where（哪裡）：在設計審查與專案會議中使用
- Why（為什麼）：縮短打樣迴圈，提高設計效率，降低成本與風險
- How（怎麼做）：透過 AI 輔助設計審查，結合 CAD 解析與知識檢索

### 2. 金字塔原理
```
大目標：提升 RD 設計效率與產品量產可行性
├── 子目標 1：設計初期多面向審查
│   ├── 任務 1-1：解析 STEP 檔案提取結構特徵
│   └── 任務 1-2：生成設計審查清單
├── 子目標 2：提供設變建議與比較報告
│   ├── 任務 2-1：多目標權衡分析
│   └── 任務 2-2：整合專利與對照表知識
└── 子目標 3：形成閉環學習
    ├── 任務 3-1：記錄 RD 回饋
    └── 任務 3-2：更新專案對照表
```

### 3. MVP 思維
**M**inimum（最小）**V**iable（可行）**P**roduct（產品）
- 先做最核心的功能：STEP 檔案解析與設變建議報告
- 後續再加強：回饋閉環與知識庫擴展
- 快速驗證：設計審查 Copilot 是否能省時並被 RD 接受

## 🎪 動手練習
選擇 RD 設計改進需求，用上面的方法拆解：
1. **你的專案是什麼？**
   提升產品設計效率，實現降成本、減重、縮短軸向的目標
2. **為什麼要做這個？**（真正的問題）
   現有設計無法量產，RD 需要在設計初期找到可行方向，避免事後試錯
3. **用戶會怎麼使用？**（使用流程）
   上傳設計檔案與約束 → 系統分析並生成報告 → RD 選擇方向並回饋
4. **需要哪些技術功能？**
   CAD 解析、多目標權衡、知識檢索、建議生成、回饋閉環
5. **分成幾個開發階段？**
   第一階段：基礎檔案解析與介面；第二階段：核心建議與報告；第三階段：閉環學習與優化

# 📋 RD 設計審查 Copilot - 產品需求文件 (PRD)

## 🎯 產品願景
打造一個智能設計審查 Copilot，協助 RD 在設計初期進行多面向審查與設變探索，縮短打樣迴圈，提升產品量產可行性，實現降成本、減重與縮短軸向的目標。

## 🔍 問題定義
### 現狀痛點
1. **設計試錯成本高**：現有設計無法量產（成本高、重量重、軸向長），需多次打樣迭代
2. **初期方向不明確**：RD 缺乏系統化工具在設計初期評估多面向影響（成本、重量、NVH 等）
3. **知識分散難利用**：專案對照表、專利搜尋結果等資料未被有效整合進設計決策
4. **會議效率低**：缺乏結構化比較報告，討論常流於主觀或重複試錯

### 目標用戶
- **主要用戶**：機構 RD（設計/設變）、系統 RD（整機整合）、製造工程（DFM/DFA）
- **共同決策者**：PM/專案、成本/採購、品質/測試（NVH/可靠度）
- **知識提供者**：老師傅/維修/試產（失效模式、裝配雷點）
- **使用場景**：設計初期審查會議、設變方向討論、最小打樣規劃
- **技術水平**：熟悉 CAD 與設計流程，能提供 STEP 檔案與約束條件

## 🎯 產品目標
### 核心目標
- 將設計審查從事後試錯前移到 Day 1，縮短打樣迴圈（從數週縮短至數天）
- 提供多面向設變建議，平衡成本、重量、NVH 等目標
- 整合專案對照表與專利知識，提升決策效率與可追溯性

### 成功指標
- RD 設計迭代週期縮短 > 30%
- 設計審查會議效率提升（報告準備時間縮短至 1 小時內）
- 用戶滿意度 > 4.0/5.0

## ⭐ 核心功能
### 1. 設計檔案解析
- **輸入**：STEP 檔案、BOM 表、設計約束（扭矩、空間、成本上限）
- **處理**：提取結構特徵（齒輪級數、軸向堆疊、標準件比例等）
- **輸出**：設計現況摘要報告

### 2. 多維度設變建議
- **功能**：基於設計現況與約束，生成 3-5 個設變方向（降重、縮軸向、降成本）
- **內容**：每個方案的預期改善幅度、代價、風險、需驗證假設

### 3. 設計審查清單生成
- **功能**：依產品特性自動生成審查清單
- **範例**：齒輪、軸承、殼體、密封、裝配、公差鏈、NVH、熱路徑

### 4. 最小打樣建議
- **功能**：針對設變方向，提供「下一步要驗證什麼」的實驗建議
- **目標**：將打樣轉為帶假設的驗證，避免盲做

### 5. 知識檢索與證據鏈
- **功能**：整合專案對照表與專利搜尋結果，生成可追溯建議
- **輸出**：每個建議連結至對照表條目、專利內容或過往測試紀錄

### 6. 一頁式比較報告
- **功能**：將設變建議、風險與驗證方向整理成會議用報告
- **便利性**：直接用於設計審查與專案討論

### 7. 回饋閉環與知識沉澱
- **功能**：RD 回饋會議結論與驗證結果，系統更新對照表
- **目標**：形成可累積的設計知識資產

## 🏗️ 技術架構概述
### 前端
- Web 或桌面應用介面（檔案上傳、約束輸入）
- 結果展示：比較報告與審查清單視覺化
- 回饋輸入：意見與結論記錄

### 後端
- CAD 解析模組：STEP 檔案結構特徵提取
- 分析引擎：多目標權衡與設變建議生成
- 知識檢索系統：專案對照表與專利數據庫整合
- 報告生成：結構化比較報告與清單輸出

### AI 整合
- CAD 理解模型：結構特徵提取
- 多目標優化算法：權衡成本、重量、NVH 等
- 檢索增強（RAG）：結合對照表與專利生成建議
