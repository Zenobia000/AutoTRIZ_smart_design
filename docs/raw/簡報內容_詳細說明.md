# RD Design Copilot 簡報內容詳細說明

---

## 1. 客戶設計痛點

### 1.1 核心痛點：早期設計的「三重困境」

```
┌─────────────────────────────────────────────────────────────────┐
│                     早期設計三重困境                             │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│    ┌──────────────┐                                             │
│    │   未知最多   │ ← 沒有量測資料、模擬不完整                  │
│    └──────┬───────┘                                             │
│           │                                                      │
│           ↓                                                      │
│    ┌──────────────┐                                             │
│    │   決策最重   │ ← 架構選錯，後期改不動                      │
│    └──────┬───────┘                                             │
│           │                                                      │
│           ↓                                                      │
│    ┌──────────────┐                                             │
│    │   時間最緊   │ ← 客戶要快、老闆要省、RD 要穩               │
│    └──────────────┘                                             │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 1.2 具體痛點清單

| 痛點 | 現象 | 後果 |
|------|------|------|
| **經驗鎖定** | RD 傾向用熟悉的方案，跳過探索 | 錯過更好的架構，早期就鎖死 |
| **腦內庫存有限** | 創意依賴個人經驗，跨域知識不足 | SCAMPER/TRIZ 問得出來，答不出來 |
| **假設隱藏** | 大家「以為」的前提沒被翻出來 | 後期才發現假設是錯的，大返工 |
| **風險後置** | 問題拖到 prototype 才爆 | 時間成本、材料成本、信任成本 |
| **決策不可追溯** | 當初為什麼選這個方案？沒人記得 | 換人就斷鏈，經驗無法沉澱 |
| **溝通斷層** | RD、PM、老闆各說各話 | 反覆對齊、反覆修改、反覆開會 |

### 1.3 痛點量化（可用於簡報）

> **典型專案數據**（可依客戶實際情況調整）
> - 早期概念階段的決策，影響 **70%** 的最終成本
> - 但這階段只有 **<10%** 的資訊是確定的
> - **60%** 的設計變更源自「早期沒想到的事」
> - 平均 **3-5 次** 架構級返工才能定案

### 1.4 痛點故事版（用於簡報開場）

```
傳統流程：

PM 丟需求 → RD 腦中搜尋 → 選一個「應該可以」的方案
         → 畫圖、建模、做 prototype
         → 測試發現問題 → 改設計
         → 再測、再改...
         → 終於過了（但已經晚了 3 個月）

問題在哪？
- 「應該可以」是假設，沒人驗證
- 「選一個」是鎖定，沒有備援
- 「測試發現」是後置，代價最高
```

## 2. RD Design Copilot 價值主張

### 2.1 一句話定位

> **把「未知」變成「可追蹤的假設」，把「靈感」變成「可審查的方案」，把「試錯」變成「最小實驗」。**

### 2.2 核心價值三角

```
                    ┌─────────────────┐
                    │   減少返工      │
                    │ (早期驗證假設)  │
                    └────────┬────────┘
                             │
              ┌──────────────┼──────────────┐
              │              │              │
              ↓              ↓              ↓
    ┌─────────────────┐           ┌─────────────────┐
    │   擴大可能性    │           │   加速對齊      │
    │ (跨域知識庫)    │           │ (結構化溝通)    │
    └─────────────────┘           └─────────────────┘
```

### 2.3 價值主張對照表

| 痛點 | RD Design Copilot 解法 | 價值 |
|------|----------------------|------|
| 經驗鎖定 | Set-Based 多路線並行 | 不過早收斂，保留備援 |
| 腦內庫存有限 | AI 跨域知識庫 + SCAMPER/TRIZ 引擎 | 擴大可能性空間 10x |
| 假設隱藏 | 假設台帳 + 索克拉底問答 | 未知可見、可追蹤 |
| 風險後置 | 最小實驗 + KT 風險評估 | 早期驗證，快速失敗 |
| 決策不可追溯 | KT 決策記錄 + 證據鏈 | 決策可審查、可複用 |
| 溝通斷層 | 一頁式 + 結構化輸出 | 跨層級對齊效率提升 |

### 2.4 價值主張故事版（用於簡報）

```
RD Design Copilot 流程：

PM 丟需求 → Copilot 結構化問題（5W1H + 索克拉底）
         → 識別矛盾、建立假設台帳
         → TRIZ + SCAMPER 生成多方案（AI 擴大可能性）
         → KT 篩選（MUST 淘汰 + WANT 評分 + 風險評估）
         → 保留 3 條路線 + 最小實驗
         → 早期驗證、快速收斂
         → 決策記錄沉澱為資產

差別在哪？
- 「應該可以」→ 假設台帳，可追蹤
- 「選一個」→ Set-Based，有備援
- 「測試發現」→ 最小實驗，前置驗證
```

### 2.5 量化價值（可用於 ROI 計算）

| 指標 | 傳統流程 | 使用 Copilot | 改善幅度 |
|------|---------|-------------|---------|
| 架構級返工次數 | 3-5 次 | 1-2 次 | **-60%** |
| 概念評審效率 | 3-4 小時/次 | 1-2 小時/次 | **-50%** |
| 假設驗證覆蓋率 | <30% | >80% | **+170%** |
| 知識沉澱率 | 低（在人腦中） | 高（在系統中） | 可複用 |

## 3. 與 ChatGPT/Gemini 等通用 LLM 的差異

### 3.1 核心差異：專用 vs 通用

```
┌─────────────────────────────────────────────────────────────────┐
│                    產品定位差異                                  │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  ChatGPT/Gemini                RD Design Copilot                │
│  ┌──────────────┐              ┌──────────────┐                 │
│  │  通用對話    │              │  專用流程    │                 │
│  │  隨問隨答    │              │  結構化引導  │                 │
│  │  一次性輸出  │              │  可追蹤記錄  │                 │
│  │  AI 自由發揮 │              │  AI 受約束   │                 │
│  └──────────────┘              └──────────────┘                 │
│                                                                  │
│  適合：探索、學習、草稿         適合：正式設計、決策、審查      │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 3.2 五大關鍵差異

| 維度 | ChatGPT/Gemini | RD Design Copilot |
|------|---------------|-------------------|
| **流程** | 無結構，自由對話 | 8 步驟結構化流程，每步有 Gate |
| **輸出** | 自由格式，不一致 | 固定規格（TRIZ/SCAMPER/KT 模板） |
| **評分** | AI 主觀判斷 | 基於證據，人做最終評分 |
| **追蹤** | 對話結束即消失 | 假設台帳 + 決策記錄，可追溯 |
| **審查** | 不可審查 | 每個輸出都有證據鏈，可進設計審查 |

### 3.3 「AI 幻覺」風險對比

| 風險 | ChatGPT/Gemini | RD Design Copilot |
|------|---------------|-------------------|
| AI 編造數據 | 常見，需人工驗證 | 強制附「證據來源」，無證據 = 標示未知 |
| AI 過度自信 | 常見，語氣肯定 | 強制列「假設清單」，明確標示前提 |
| AI 忽略風險 | 常見，傾向樂觀 | 強制做「黑帽審查」+ KT 風險評估 |
| AI 給出最優解 | 常見，單一答案 | 強制保留「Set-Based 多路線」 |

### 3.4 價值對比表（用於簡報）

| 能力 | ChatGPT | Gemini | RD Design Copilot |
|------|---------|--------|-------------------|
| 知識庫廣度 | 高 | 高 | 高 + 領域專用 |
| 結構化流程 | 無 | 無 | **8 步驟 + Gate** |
| 輸出格式一致性 | 低 | 低 | **固定模板** |
| 假設追蹤 | 無 | 無 | **假設台帳** |
| 決策記錄 | 無 | 無 | **KT 記錄 + 簽核** |
| 風險治理 | 無 | 無 | **SWOT + AC** |
| 設計審查適用 | 低 | 低 | **高（有證據鏈）** |
| 責任歸屬 | 模糊 | 模糊 | **明確（人簽核）** |

### 3.5 定位聲明（用於簡報）

> **RD Design Copilot 不是要取代 ChatGPT/Gemini，而是在它們之上加入「工程治理層」。**
>
> - ChatGPT/Gemini：適合探索、學習、草稿
> - RD Design Copilot：適合正式設計、決策、審查
>
> **核心差異：我們不是讓 AI 更聰明，而是讓 AI 的輸出「可審查、可追蹤、可負責」。**

### 4.2 各階段詳細產出

#### Phase I: 定義問題空間

| 產出 | 格式 | 內容 | 用途 |
|------|------|------|------|
| **任務定義表** | 結構化表格 | Mission + Hard/Soft/Non-goals + 三個最不能失敗指標 | 對齊需求、設定邊界 |
| **索克拉底問題樹** | 樹狀圖/清單 | 6 類提問（澄清/假設/證據/觀點/後果/反思） | 翻出隱藏假設 |
| **矛盾列表** | TRIZ 句式表格 | 改善參數 vs 惡化參數 + 工程表述 + 物理矛盾 | 為發散做準備 |
| **因果迴路圖** | Mermaid/Visio | 熱-機-振耦合關係 + 正回饋迴路 + 斷路點 | 識別風險放大點 |

#### Phase II: 假設與發散

| 產出 | 格式 | 內容 | 用途 |
|------|------|------|------|
| **假設台帳** | 6 欄表格 | 假設內容/依據/後果/驗證方法/成本/週期 | 追蹤未知 |
| **TRIZ 解法表** | YAML/表格 | 矛盾句/採用原理/抽象策略/工程對映/代價/最小實驗 | 結構化創意 |
| **SCAMPER 變形表** | 7 欄表格 | 動作/對象/機制/失效模式/風險/假設/驗證 | 模組級變形 |
| **方案集合** | 結構化清單 | 3-5 條架構級路線，每條含機制+假設+風險+驗證 | Set-Based 設計 |

#### Phase III: 收斂與驗證

| 產出 | 格式 | 內容 | 用途 |
|------|------|------|------|
| **SWOT 分析** | 2x2 矩陣 | 內部強弱 + 外部機會威脅 | 全方位檢視 |
| **風險登錄表** | 表格 | 風險描述/機率/衝擊/Owner/緩解/監控 | 風險治理 |
| **KT 決策記錄** | YAML/表格 | MUST 結果/WANT 評分/風險評估/決策理由/行動項目/簽核 | 可追溯決策 |
| **最小實驗設計** | 表格 | 驗證假設/目標/方法/成功標準/失敗後果/週期成本 | 早期驗證 |

#### 溝通與沉澱

| 產出 | 格式 | 內容 | 用途 |
|------|------|------|------|
| **一頁式摘要** | 固定模板 | 選了什麼/為何 Robust/未知管理/下一步/需要支援 | 向上報告 |
| **RD FAQ** | Q&A 表格 | 常見疑慮與標準答案 | 團隊對齊 |
| **Playbook** | 知識庫 | MUST/WANT 模板 + 失效路徑庫 + 約束庫 | 下一案複用 |

### 4.3 產出範例（可用於 Demo）

**範例：TRIZ 解法表**

```yaml
TRIZ_解法_C1:
```

### 5.2 詳細資料需求

#### 必要資料

| 資料 | 格式 | 最低要求 | 用途 |
|------|------|---------|------|
| **需求規格書** | 文件/草稿 | 功能需求 + 使用情境 | Step 1 問題界定 |
| **硬約束清單** | 表格 | 空間、成本、法規、時程 | MUST 條件定義 |
| **三個最不能失敗指標** | 清單 | 至少說出「最怕什麼」 | 優先級設定 |

#### 建議資料

| 資料 | 格式 | 說明 | 用途 |
|------|------|------|------|
| **過往案例** | 文件/口述 | 成功案例學什麼、失敗案例避什麼 | 假設台帳初始化 |
| **Know-how 文件** | 任意 | 設計規範、經驗法則、踩過的坑 | AI 知識庫擴充 |
| **AVL 供應商清單** | 表格 | 關鍵件供應商數量 | 供應風險評估 |
| **製程能力** | 文件/數據 | 公差、良率、產能 | 可行性判斷 |

#### 過程中需參與

| 參與項目 | 參與者 | 時間點 | 說明 |
|---------|-------|--------|------|
| **MUST 條件定義** | 團隊 | Phase I | 哪些是「不可妥協」的硬約束 |
| **WANT 權重共識** | 團隊 | Phase II | 各維度的優先級排序 |
| **假設驗證判斷** | 工程師 | Phase II-III | AI 不能判斷假設對錯 |
| **風險機率/嚴重度** | 工程師 | Phase III | AI 識別風險，人判斷等級 |
| **最終決策簽核** | 負責人 | Phase III | 責任歸屬明確 |

### 5.3 資料品質 vs 產出品質

| 資料完整度 | 可達成的產出 | 限制 |
|-----------|-------------|------|
| **最低**（只有需求+硬約束） | 結構化問題定義 + 矛盾識別 + 方案草稿 | 假設多、驗證成本高 |
| **中等**（+過往案例+AVL） | 較精準的假設台帳 + 供應風險評估 | 仍需大量工程判斷 |
| **完整**（+know-how+製程） | 高品質方案集合 + 可執行的最小實驗 | 接近正式設計審查 |

### 5.4 客戶承諾聲明（可用於合約）

> **客戶同意提供以下資料，以確保 RD Design Copilot 產出品質：**
>
> **必要項目**（無法啟動）：
> - [ ] 需求規格書或等效文件
> - [ ] 硬約束清單（空間/成本/法規/時程）
> - [ ] 「三個最不能失敗的指標」
>
> **參與承諾**（無法替代）：
> - [ ] 團隊參與 MUST/WANT 條件定義
> - [ ] 工程師參與假設驗證判斷
> - [ ] 負責人簽核最終決策
>
> **理解事項**：
> - AI 擴大可能性，但不做最終判斷
> - 每個評分都需要證據，不是 AI 主觀
> - 決策責任在人，AI 是副駕

### 6.2 短期擴展詳細說明

#### 6.2.1 設計審查 Copilot

| 項目 | 說明 |
|------|------|
| **目標** | 自動化設計審查準備 + 審查會議輔助 |
| **功能** | 審查清單生成、證據完整性檢查、審查記錄結構化 |
| **整合點** | 承接 KT 決策記錄，自動生成審查 checklist |
| **價值** | 審查會議效率提升 50%，審查紀錄可追溯 |

| 項目 | 說明 |

**預期產出**：
- DFM checklist（每方案）
- 公差敏感度報告
- 組裝順序建議
- 製程風險登錄表

### 建議簡報流程（20 分鐘版）

| 時間 | 內容 | 頁數 |

### 關鍵訊息（一句話版）

1. **痛點**：早期最不確定，但決策影響最大，傳統流程是「試了才知道」
2. **價值**：把「未知」變「可追蹤」，把「試錯」變「最小實驗」
3. **差異**：不是讓 AI 更聰明，而是讓 AI 的輸出「可審查、可追蹤、可負責」
4. **產出**：結構化文件，可進設計審查，可沉澱為資產
5. **Commit**：需求 + 硬約束 + 團隊參與，AI 是副駕不是駕駛
6. **未來**：從概念設計延伸到審查、製造、驗證的全生命週期
