# KT × Robust 決策框架

**一句話定位**：用 Kepner-Tregoe 的結構化決策分析，把模糊的 Robust 評分變成「可觀察、可驗證、可審查」的工程判斷。

---

## 問題診斷：為什麼原本的 Robust 評分不夠好？

| 問題 | 後果 | KT 如何解決 |
|------|------|------------|
| 指標定義模糊 | 不同人給不同分數 | MUST/WANT 用工程條件定義，不是形容詞 |
| 依賴 AI 主觀判斷 | 無法審查、無法追責 | 每個評分必須附「證據」 |
| 缺乏淘汰機制 | 脆弱方案混進候選 | MUST 條件不過直接淘汰 |
| 風險評估分離 | 決策與風險脫鉤 | Adverse Consequences 整合進評分 |

---

## KT 決策分析核心結構

```
┌─────────────────────────────────────────────────────────────────┐
│                    KT Decision Analysis                          │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  Stage 1: 定義決策聲明 (Decision Statement)                      │
│  ┌─────────────────────────────────────────────────────────────┐│
│  │ "選擇一個【最能抵抗未知變異】的設計方案"                      ││
│  └─────────────────────────────────────────────────────────────┘│
│                              ↓                                   │
│  Stage 2: MUST 條件 (Go/No-Go)                                   │
│  ┌─────────────────────────────────────────────────────────────┐│
│  │ 不滿足 → 直接淘汰，不進入評分                                ││
│  └─────────────────────────────────────────────────────────────┘│
│                              ↓                                   │
│  Stage 3: WANT 條件 (加權評分)                                   │
│  ┌─────────────────────────────────────────────────────────────┐│
│  │ 權重(1-10) × 滿足程度(1-10) = 加權分數                       ││
│  └─────────────────────────────────────────────────────────────┘│
│                              ↓                                   │
│  Stage 4: Adverse Consequences (風險扣分)                        │
│  ┌─────────────────────────────────────────────────────────────┐│
│  │ 機率(H/M/L) × 嚴重度(H/M/L) = 風險等級 → 扣分或淘汰         ││
│  └─────────────────────────────────────────────────────────────┘│
│                              ↓                                   │
│  Stage 5: 決策 (最高淨分 + 風險可接受)                           │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

# Stage 1: 決策聲明

## 1.1 標準格式

```
決策聲明：選擇一個 [目標描述]，滿足 [關鍵約束]，以達成 [預期結果]。
```

## 1.2 範例

```
決策聲明：選擇一個「馬達-減速機整合架構」，
         滿足「空間 < 150mm、成本 < $200、NVH < 65dB」，
         以達成「在早期未知最多時，設計最不容易翻車」。
```

# Stage 2: MUST 條件（Go/No-Go 淘汰關）

## 2.1 核心原則

> **MUST 條件是「不可妥協」的硬約束。不滿足 = 直接淘汰，不進入評分階段。**

## 2.2 MUST 條件定義規則

| 規則 | 說明 | 錯誤示範 | 正確示範 |
|------|------|---------|---------|
| **可量測** | 必須有數字或明確判斷 | "散熱要好" | "穩態溫升 < 40K" |
| **有來源** | 必須說明約束從哪來 | "體積要小" | "體積 < 1.5L（客戶規格 REQ-003）" |
| **二元判斷** | 只有 Pass/Fail，不能「差一點」 | "成本盡量低" | "BOM 成本 ≤ $180" |

## 2.3 Robust 轉 MUST 條件對照表

| 原 Robust 維度 | MUST 條件轉換 | 判斷方式 |
|---------------|--------------|---------|
| **Margin** | 三個最不能失敗指標都有 ≥10% 餘裕 | 計算或估算 |
| **Decoupling** | 關鍵失效路徑不超過 2 個耦合點 | 因果迴路圖審查 |
| **Recoverability** | 存在至少 1 條備援/調整路徑 | 設計審查 |
| **Complexity** | 新增零件 ≤ N 個（依專案定） | 零件清單 |
| **Sensitivity** | 無「公差敏感紅區」（單一公差影響 >30% 性能） | 敏感度分析 |
| **SupplyRisk** | 關鍵件至少 2 家供應商可選 | 供應商清單 |

## 2.4 MUST 條件模板

```yaml
MUST_條件清單:
  M1_空間約束:
    條件: 整體體積 ≤ 1.5L
    來源: 客戶規格 REQ-003
    判斷方式: 3D 模型量測

  M2_成本上限:
    條件: BOM 成本 ≤ $180
    來源: PM 預算限制
    判斷方式: 報價單

  M3_安全餘裕:
    條件: 溫升、NVH、壽命三指標均有 ≥10% margin
    來源: Robust 設計原則
    判斷方式: 估算表（附假設）

  M4_解耦程度:
    條件: 熱-振-機 三域耦合點 ≤ 2
    來源: 因果迴路圖
    判斷方式: 設計審查

  M5_供應安全:
    條件: 關鍵件（馬達、減速機、控制器）各有 ≥2 家供應商
    來源: 供應鏈政策
    判斷方式: AVL 清單
```

## 2.5 MUST 評估表

| 方案 | M1 空間 | M2 成本 | M3 餘裕 | M4 解耦 | M5 供應 | 結果 |
|------|--------|--------|--------|--------|--------|------|
| A | ✓ | ✓ | ✓ | ✓ | ✓ | **PASS** |
| B | ✓ | ✗ | ✓ | ✓ | ✓ | **FAIL** |
| C | ✓ | ✓ | ✗ | ✓ | ✓ | **FAIL** |

> **任一 MUST 不過 = 直接淘汰**

# Stage 3: WANT 條件（加權評分）

## 3.1 核心原則

> **WANT 條件是「希望有但可妥協」的目標。用 權重 × 滿足程度 計算加權分數。**

## 3.2 評分規則

- **權重 (Weight)**: 1-10，由決策團隊在評分前共識
- **滿足程度 (Score)**: 1-10，基於「可觀察的工程條件」評定
- **加權分數**: Weight × Score

## 3.3 Robust 轉 WANT 條件（含評分標準）

### W1: 安全餘裕深度 (Margin Depth)

| 分數 | 條件 | 證據要求 |
|------|------|---------|
| 10 | 三指標餘裕均 ≥50% | 計算書 |
| 8 | 三指標餘裕均 ≥30% | 計算書 |
| 6 | 三指標餘裕均 ≥20% | 計算書 |
| 4 | 三指標餘裕均 ≥10%（剛過 MUST） | 計算書 |
| 2 | 有一指標餘裕 <10% 但 >0 | 計算書 + 風險說明 |

### W2: 系統解耦程度 (Decoupling Level)

| 分數 | 條件 | 證據要求 |
|------|------|---------|
| 10 | 熱/振/機 完全獨立，無共用路徑 | 因果迴路圖 |
| 8 | 耦合點 = 1，且有隔離設計 | 因果迴路圖 + 設計說明 |
| 6 | 耦合點 = 2（剛過 MUST） | 因果迴路圖 |
| 4 | 耦合點 = 3，有緩解措施 | 因果迴路圖 + 緩解說明 |
| 2 | 耦合點 ≥4，高風險 | 因果迴路圖 + 風險登錄 |

### W3: 可恢復性 (Recoverability)

| 分數 | 條件 | 證據要求 |
|------|------|---------|
| 10 | 模組化設計，任一模組可熱插拔更換 | 組裝圖 + 維修程序 |
| 8 | 主要模組可現場更換，<30min | 維修程序 |
| 6 | 可現場調整/校正，有調整機構 | 設計說明 |
| 4 | 需返廠維修，但有明確程序 | 維修程序 |
| 2 | 無法維修，只能整機更換 | - |

### W4: 設計簡潔度 (Simplicity)

| 分數 | 條件 | 證據要求 |
|------|------|---------|
| 10 | 零件數 ≤ 基準 -30% | BOM |
| 8 | 零件數 ≤ 基準 -15% | BOM |
| 6 | 零件數 = 基準 ±10% | BOM |
| 4 | 零件數 = 基準 +15~30% | BOM + 必要性說明 |
| 2 | 零件數 > 基準 +30% | BOM + 風險說明 |

### W5: 公差鈍感度 (Tolerance Robustness)

| 分數 | 條件 | 證據要求 |
|------|------|---------|
| 10 | 無敏感公差（單一公差變化對性能影響 <5%） | 敏感度分析 |
| 8 | 敏感公差 ≤1 個，有自校正機構 | 敏感度分析 + 設計說明 |
| 6 | 敏感公差 ≤2 個，有明確管控 | 敏感度分析 + 管控計畫 |
| 4 | 敏感公差 3-4 個 | 敏感度分析 + 風險登錄 |
| 2 | 敏感公差 ≥5 個，高度依賴製程能力 | 敏感度分析 + 風險說明 |

### W6: 供應鏈韌性 (Supply Resilience)

| 分數 | 條件 | 證據要求 |
|------|------|---------|
| 10 | 全部採用通用件，≥3 家供應商 | AVL |
| 8 | 關鍵件 ≥3 家，其他 ≥2 家 | AVL |
| 6 | 關鍵件 ≥2 家（剛過 MUST） | AVL |
| 4 | 有 1 個關鍵件為獨家，但有替代設計 | AVL + 替代方案 |
| 2 | 多個關鍵件為獨家，無替代 | AVL + 風險說明 |

### W7: 驗證可行性 (Verifiability)

| 分數 | 條件 | 證據要求 |
|------|------|---------|
| 10 | 所有關鍵假設可在 1 週內驗證 | 驗證計畫 |
| 8 | 關鍵假設可在 2 週內驗證 | 驗證計畫 |
| 6 | 關鍵假設可在 4 週內驗證 | 驗證計畫 |
| 4 | 部分假設需 >4 週或昂貴測試 | 驗證計畫 + 成本估算 |
| 2 | 關鍵假設無法在 prototype 前驗證 | 風險說明 |

# Stage 4: Adverse Consequences（風險評估）

## 4.1 核心原則

> **即使 WANT 分數最高，如果風險不可接受，仍可能被否決。**

## 4.2 風險評估矩陣

```
            嚴重度
            Low    Medium    High
機    High    M       H        H*
率    Medium  L       M        H
      Low     L       L        M

L = Low Risk（可接受）
M = Medium Risk（需緩解措施）
H = High Risk（需顯著緩解或重新考慮）
H* = 極高風險（考慮淘汰）
```

## 4.3 風險識別清單（每方案必做）

| 風險類型 | 檢查問題 |
|---------|---------|
| **技術風險** | 有哪些假設是第一次做？沒有案例支撐？ |
| **製程風險** | 有哪些加工/組裝是挑戰現有能力的？ |
| **供應風險** | 有哪些零件交期長、獨家、價格波動？ |
| **整合風險** | 有哪些介面是新的？耦合是複雜的？ |
| **驗證風險** | 有哪些關鍵特性無法在早期驗證？ |
| **量產風險** | 從 prototype 到量產有哪些落差？ |

## 4.4 Adverse Consequences 評估表

| 方案 | 風險描述 | 機率 | 嚴重度 | 等級 | 緩解措施 | 殘餘風險 |
|------|---------|------|--------|------|---------|---------|
| A | 新材料熱膨脹未驗證 | M | H | **H** | 最小實驗 | M |
| A | 組裝順序複雜 | L | M | **L** | SOP 文件化 | L |
| C | 獨家供應商 | M | H | **H** | 開發替代 | M |
| D | 驗證週期長 | H | M | **H** | 分階段驗證 | M |

## 4.5 風險調整決策

| 情況 | 決策 |
|------|------|
| 所有風險 ≤ M | 選擇 WANT 總分最高者 |
| 有 H 風險但有緩解 | 緩解措施納入行動計畫，可選擇 |
| 有 H* 風險 | 重新審視是否淘汰 |
| 多個 H 風險 | 考慮是否值得冒險 |

# AI 在 KT 流程中的角色定義

## 可以做（有價值）

| 任務 | AI 角色 | 人的角色 |
|------|--------|---------|
| 列出 MUST 候選條件 | 提供建議清單 | 決定哪些是真正的 MUST |
| 生成 WANT 評分標準草案 | 基於工程原則建議 | 審核並調整 |
| 識別風險 | 系統性掃描潛在風險 | 判斷機率與嚴重度 |
| 收集證據 | 整理相關資料 | 判斷證據是否充分 |
| 生成決策記錄草稿 | 格式化輸出 | 審核並簽核 |

## 不可以做（必須由人決定）

| 任務 | 原因 |
|------|------|
| 決定 MUST 條件的值 | 這是業務/技術約束，需要 owner 確認 |
| 決定 WANT 權重 | 這反映團隊優先級，需要共識 |
| 給出最終評分 | 評分需要基於證據，AI 只能建議 |
| 判斷風險機率/嚴重度 | 這需要工程判斷和經驗 |
| 做出最終決策 | 決策責任在人，AI 只是工具 |

# 整合到主流程

## 在 Step 3.2（決策與行動）中替換原有 Robust 評分

```
原流程:
  Step 3.2 → Robust 評分公式 → 最小實驗

新流程:
  Step 3.2 → KT Decision Analysis
           ├── MUST 篩選（淘汰不合格）
           ├── WANT 評分（加權排序）
           ├── Adverse Consequences（風險調整）
           └── 決策記錄 + 最小實驗
```

## MUST vs WANT 判斷

| 問題 | MUST | WANT |
|------|------|------|
| 不滿足會怎樣？ | 不能用 | 不完美但可用 |
| 可以妥協嗎？ | 不行 | 可以 trade-off |
| 評分方式？ | Pass/Fail | 1-10 分 |

## 評分流程速查

```
1. 列出所有方案
2. 定義 MUST 條件 → 淘汰不合格
3. 定義 WANT 條件 + 權重 → 團隊共識
4. 逐方案評分 → 基於證據
5. 識別風險 → AI 輔助 + 人判斷
6. 計算淨分 → WANT 分 - 風險影響
7. 決策 + 記錄 → 人簽核
```
